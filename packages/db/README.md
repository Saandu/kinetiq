# Database foundation

The package supplies the 18 planned application tables, a Drizzle schema, reviewed SQL migrations, an explicit development seed, fixed service pool budgets, a transaction-local tenant helper and an atomic telemetry batch insert. It uses native TypeScript 7.

The initial table definitions were generated by Drizzle Kit; range-partition clauses were added before applying the initial migration. PostgreSQL-specific policies, grants, checks, indexes and extension setup are reviewed SQL in the following migration. Future generated migrations must be reviewed against these hand-written features. Production migrations must follow the plan's backward-compatible expand/contract rule.

## Run the checks

Docker Desktop must be running with Linux containers. Node 24.21.0 and Docker's CLI must be on PATH. From the repository root:

```sh
npm ci
npm run verify
```

Verification builds `kinetiq-postgres:18.6-1` and runs Testcontainers against that image. Tests generate temporary credentials, use real service logins, seed two tenants and remove the test container afterwards. The image remains cached. Tests do not touch a persistent development database or cloud resources.

For targeted work:

```sh
npm run db:image
npm run build --workspace @kinetiq/contracts
npm run test --workspace @kinetiq/db
npm run schema:generate --workspace @kinetiq/db
```

## Roles and tenant context

Migrations create `kinetiq_api`, `kinetiq_ingest`, `kinetiq_analytics` and `kinetiq_alerts` as unprivileged NOLOGIN roles. Tests temporarily enable login with randomly generated passwords. Compose and CloudNativePG must provision their own credentials; no service password is committed. Migration/seed commands use a separate privileged identity through `DATABASE_URL`.

All tenant parent tables enable and force RLS. Missing context returns no rows; writes cannot claim another tenant. Composite foreign keys also bind children to their parent machine/site/user's organization. Non-superuser owners are subject to RLS; superusers bypass it, so runtime services cannot use the migration identity.

Services use `withTenantTransaction(pool, trustedOrganizationId, action)`. It begins a transaction, calls parameterized `set_config(..., true)` (transaction-local), executes the action and commits or rolls back before releasing the connection. A failed rollback discards the connection. Never use a session-level tenant setting.

RLS protects against accidental missing query filters; a trusted backend credential can still set another tenant UUID. Authentication and authorization must resolve the organization before this helper is called. It is not safe to expose SQL access or accept tenant identity from a request body.

`createServicePool` requires the matching role identity and caps API/ingest/alerts/analytics pools at 5/3/2/2. The separate API LISTEN connection and maximum replica budget will be checked in Helm during Phase 1.

## Telemetry and partitions

`insertTelemetryBatch` validates the batch, matches payload identity against a trusted device envelope and verifies the device mapping inside the tenant transaction. It inserts all readings with `ON CONFLICT (machine_id, ts) DO NOTHING`, advances `last_seen_at` monotonically and notifies listeners when new rows were inserted. A failure rolls everything back. PostgreSQL delivers NOTIFY only after commit; a queue consumer must delete the message only after this function succeeds. Sequence numbers are not used to reject valid reordered batches.

Ingest can insert telemetry and read its conflict-key columns; it cannot read sensor values or delete telemetry. It can read the device identity/last-seen columns and update only `last_seen_at`. API cannot write telemetry or derived health. Audit writes are append-only for API. Analytics cannot edit model settings. Alerts uses its separate role.

Telemetry is range-partitioned daily in UTC. `pg_partman` prepares seven days ahead and drops expired daily partitions after 30 days. This is a partition-level retention window, not an exact row-by-row 30-day cutoff. Health is partitioned monthly. Runtime services use parent tables; direct child-table access is denied, including future partitions. There is no default partition silently accumulating unbounded data.

Hourly cron jobs run partition maintenance and expire 24-hour idempotency results; a daily job expires hourly aggregates after one year. Aggregate computation will be wired into the ingest/maintenance pipeline in the next implementation steps. Tests currently verify extension availability, job registration, future partition creation and actual expired-partition removal; they do not simulate a month of scheduled uptime.

## Migration safety and current boundary

The migration runner serializes concurrent runs with a transaction-scoped advisory lock and records filename/checksum pairs. Already-applied files cannot be edited, removed or inserted out of order. Checksums normalize Windows line endings. New migrations and their journal entries commit atomically; a failed migration leaves neither partial tables nor a success entry.

The database image pins PostgreSQL 18.6 by digest and PGDG `pg_partman` 5.5.0 / `pg_cron` 1.6.8 packages. It is a local Docker/Testcontainers image, not yet a validated CloudNativePG image. Production TLS, Kubernetes credentials, backups, operator compatibility and cluster-wide connection budgets remain Phase 1/2 work.

The development seed preserves the current eight fictional demo machines and IDs; the simulator will add configurable scale in its implementation step. It does not seed Cognito users, invent measured telemetry, or claim analytics exists.

Drizzle Kit's obsolete transitive esbuild dependency is overridden to 0.28.2 at the root. Fresh installation, audit and migration generation must be checked when upgrading that override. Do not use `npm audit fix --force` to downgrade the selected Drizzle toolchain.
